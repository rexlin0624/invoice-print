# 桌面端参考（M4）

> 桌面端 = **同一个网页版 + 一层薄外壳**。业务逻辑一行都不在 Rust 里：
> 解析、去重、排版、合成打印 PDF 全在 `packages/core`（TypeScript），两个外壳共用。
>
> 这里记的是**外壳与前端之间那条契约**，以及为什么它长这样。
> 编译纪律见 `AGENTS.md` §1（本机只许 `cargo check -j 2`）。

---

## 1. 为什么要有外壳

网页版做不到的只有四件事，外壳就只做这四件：

| 网页版的难处                                     | 桌面版的做法                          |
| ------------------------------------------------ | ------------------------------------- |
| 下载只能落到「浏览器的下载目录」，用户不知道在哪 | 系统保存对话框 → 知道路径 → 能显示它  |
| `window.print()` 打的是**界面**，不是合成的 PDF  | 写临时文件 → 交给系统 `lp` / `-Verb Print` |
| `<input type=file>` 的字节要先复制进渲染进程     | 原生对话框拿路径 → 直接按路径读盘      |
| 库在 IndexedDB 里，清一次浏览数据就没了          | 数据目录里留一份清单备份 + 本地日志    |

其余一律复用：`apps/desktop/src-tauri/tauri.conf.json` 的
`build.frontendDist` 指向 `../../web/dist`，桌面端**没有自己的界面代码**。

## 2. 六个能力模块

一个模块一个文件，都在 `apps/desktop/src-tauri/src/`。命令名与前端一一对应。

| 文件        | 命令                                                                   | 干什么                                 |
| ----------- | ---------------------------------------------------------------------- | -------------------------------------- |
| `app.rs`    | `app_info`                                                             | 版本 / 平台 / **数据目录**（帮助对话框用） |
| `dialog.rs` | `pick_documents`                                                       | 原生「选择发票」多选对话框             |
| `files.rs`  | `read_document` / `save_document`                                      | 按路径读字节 / 保存对话框 + 写盘       |
| `print.rs`  | `print_document`                                                       | 写临时 PDF → 交给系统打印              |
| `shell.rs`  | `reveal_path` / `open_path`                                            | 在文件管理器里显示 / 用默认程序打开    |
| `store.rs`  | `store_list` / `store_read` / `store_write` / `store_append` / `store_remove` | 数据目录里自己的文件（库备份、日志） |

`app.rs` 还负责单实例：第二次启动不开新进程，而是把已有窗口叫到前面
（两个实例会同时打开同一份 IndexedDB 互相覆盖）。
`dialog.rs` / `files.rs` / `print.rs` 的**可测纯函数**（百分比解码、文件名清洗、
打印机名解析、数据目录名字白名单）都带 `#[cfg(test)]`，由 CI 的 `cargo test` 跑。

**为什么 `blocking_*` 只能在 async 命令里调**：它内部 `run_on_main_thread` 把对话框丢回主线程
再阻塞等结果。同步命令若本身跑在主线程上，就是死锁。所以 `pick_documents` / `save_document`
都是 `async fn`。

## 3. IPC 契约（三条约定）

前端在 `apps/web/src/lib/shell.ts`，**不用 `@tauri-apps/api`**：
我们只用到一个入口（`window.__TAURI_INTERNALS__.invoke`），为它往网页版的依赖树里
塞一个 SDK 不划算，而且版本一升网页版就多一个永远用不到的包要跟着升。

三条约定都是 Tauri v2 官方的（官方 `tauri-plugin-fs` 同样处理）：

1. **发字节**：`invoke(cmd, uint8Array, { headers })`。
   `Uint8Array` / `ArrayBuffer` 会被当作**裸请求体**发出去（`application/octet-stream`），
   所以元信息（文件名）只能走 **header**。塞进 JSON 会变成数字数组，体积膨胀 4~5 倍。
2. **收字节**：Rust 返回 `Response` 时，前端拿到的是 **`ArrayBuffer`**；
   返回普通结构体时是 JSON 对象。前端靠 `asBytes()` 收口，拿到别的就报错，
   **不静默返回空**（空字节会被误当成「解析不出字段」）。
3. **header 只收可见 ASCII**：中文文件名必须 `encodeURIComponent`，
   Rust 侧 `percent_decode` 解回来。**别改成 `JSON.stringify`** —— 它默认不转义非 ASCII，
   中文会让 `HeaderValue` 直接报错。

⚠️ 一个反直觉的点：`Option<Response>` **不是**合法的命令返回值。
Tauri 的 `IpcResponse` 只对「`Serialize` 类型」和 `Response` 本身实现，`Option<Response>` 两者都不是。
所以「文件不存在」用**空字节**表示（`store_read`），前端把空字节与「没有」当同一件事。

这套约定由 `apps/web/src/lib/shell.test.ts`（18 个用例）钉住：
发出去的 `cmd` / 请求体 / header 编码、响应形状、日志格式。
这类 bug **只有在打包好的桌面版里才会现形**，所以在单测里挡。

## 4. 前端怎么接

| 文件                             | 职责                                                                       |
| -------------------------------- | -------------------------------------------------------------------------- |
| `apps/web/src/lib/shell.ts`      | 桥本身：`isDesktop()` + 12 个命令的类型化封装 + `logLine()`                |
| `apps/web/src/lib/save.ts`       | **保存的唯一入口**：网页版 `downloadBlob`，桌面版系统对话框                |
| `apps/web/src/lib/print.ts`      | `printPdf()`：桌面版 `print_document`，网页版隐藏 iframe                   |
| `apps/web/src/lib/libraryBackup.ts` | 库清单备份：序列化 / 容错解析 / 差异 / 恢复                              |
| `apps/web/src/state/useLibraryBackup.ts` | 库页的「备份里有 N 条不在库里」                            |

页面只调 `saveBytes` / `saveText` / `printPdf`，**不判断自己跑在哪儿** ——
判断只在 `save.ts` 里做一次。`SaveOutcome.path` 只有桌面端才有值，
页面据此决定要不要给「在文件夹里显示」。

`isDesktop()` 读的是 `__TAURI_INTERNALS__`（Tauri 注入 IPC 用的，任何构建都有），
不是 `window.__TAURI__`（那要开 `withGlobalTauri`，是给不打包的前端用的）。

## 5. 库备份：为什么只备份清单

桌面版的「已报销库」还是在 IndexedDB 里（不放 Rust 侧，因为网页版也要用同一套）。
但**每次库变动**会往数据目录写一份 `library-backup.json`：

- 只存**清单**（号码、金额、购销方、状态、时间戳），不存原文件字节 ——
  原文件动辄几百 MB，每次变动重写一遍不现实；而真正丢了找不回来的是
  「这张票我报过了」这个事实，原文件用户手上还有。
- 库页自己发现「备份里有、库里没有」（清过浏览数据？）**才**显示一张卡给「从备份恢复」——
  属于「有情况才出现」那一类。
- 恢复出来的记录 `hasBytes=false`：字段、金额、状态都在，但**不能再打一份**。
  这是诚实的降级，不假装原文件还在。
- 恢复按原状态分组写，并带上**原始时间戳**（不然历史记录看起来都发生在恢复那一刻）。
- **清空本机库不会删备份**：备份就是保险，不该被一次误操作带走。
  真要删，去数据目录删文件（帮助 → 打开数据目录）。

日志是另一个文件：`logs/app.log`，追加写，超过 2 MB 轮转成 `.1`。
前端只在几个关键节点写（导入结果、保存/打印结果、读文件失败），
**发了就不管**：日志写不进去不该影响用户正在做的事。

## 6. 刻意不用的东西

| 不用的                              | 为什么                                                                       |
| ----------------------------------- | ---------------------------------------------------------------------------- |
| `tauri-plugin-fs`                   | 读写文件几行 `std::fs` 就够，还能省掉一整套 scope / ACL 权限模型             |
| `tauri-plugin-opener`               | 在访达里显示 / 用默认程序打开，每个平台就一条命令                            |
| `tauri-plugin-log`                  | 我们要的只是「追加 + 轮转」，自己 30 行搞定，还能少一个依赖                   |
| 官方打印插件                        | **不存在**。所以 `print_document` 是自己写的（macOS/Linux `lp`，Windows `-Verb Print`） |

用到的只有两个：`tauri-plugin-dialog`（原生对话框必须用官方的，没有手搓的理由）、
`tauri-plugin-single-instance`（两个实例会抢同一份 IndexedDB）。

**打印失败不算错误**：返回临时文件路径 + 一句人话，前端给「用系统程序打开」。
弹一个「打印失败」然后什么都不给，才是真的死胡同。

## 7. 构建与开发

```bash
pnpm desktop:dev     # 开发：起 web 的 Vite(5180) + Tauri 窗口，热更新照常
pnpm desktop:build   # 打包（默认禁止；本机实测可行，见 §8）
pnpm desktop:icons   # 重新生成图标（见下）
pnpm desktop:check   # cargo check --all-targets -j 2（本机唯一允许的 cargo 命令）
```

这几个脚本都过 `apps/desktop/scripts/rust.mjs` 这一层，它做四件事：

- **拦住会链接的命令**：`tauri dev` / `tauri build` / `cargo test` 在本机会被直接拒绝
  （`cargo check` 只产 metadata，放行）。要故意闯祸得先设 `ALLOW_RUST_BUILD=1`，
  CI 里 `CI=true` 自动放行。
- **起飞前自检**：会链接的命令在**启动 cargo 之前**先量一次可用内存，不到
  `RUST_MIN_FREE_MB`（默认 3000 MB）就拒绝，并把「现在最吃内存的应用」连同
  `osascript -e 'quit app "…"'` 一起打出来。理由是看门狗只能**事后**刹车，
  而链接类命令几分钟里会涨到 1 GB 上下 —— 等到越界才杀可能已经晚了。
  报告里的应用是**按应用归并**的（Chrome 的十几个 helper 算一个），
  本会话自己那条祖先进程链（终端 / 编码助手）会标成「别动」：
  内存紧张时该退应用，退终端等于把正在做的事一起退掉（而且它往往只有几十 MB）。
  `cargo check` 不链接，低于门槛只提醒、不拦。硬要跑：`RUST_SKIP_PREFLIGHT=1`。
- **内存看门狗**：命令起来之后持续采样（前 5 秒每 100 ms，之后每 2 秒），
  两条线任一越界就 SIGKILL 整棵进程树（`detached` 起的进程组，一次杀干净）：
  这棵树 RSS > `RUST_MAX_MEMORY_MB`（默认 2500 MB），
  或系统可用内存占比 < `RUST_MIN_FREE_RATIO`（默认 0.12，macOS 按
  `vm_stat` 的 free + inactive + speculative 算）。
  **宁可这次检查失败，也不要机器重启** —— 检查可以再跑，重启会带走你正在做的事。
  正常 `cargo check` 实测峰值 105–342 MB（跑完会打印峰值与采样次数），离上限很远。
- **找 cargo**：这台机器上 rustup 装了但 `~/.cargo/bin` 没写进 shell 的 rc，
  npm script 里直接写 `cargo` 只会 `command not found`。脚本按常见位置找一遍 ——
  但**只给绝对路径不够**：`tauri` 是 node 程序，它按名字去 spawn `cargo metadata`，
  所以找到之后还要把这个目录塞进子进程的 `PATH`。第一次打正式包就是栽在这儿的
  （报 `failed to run 'cargo metadata' … No such file or directory`）。

`tauri.conf.json` 里几个有意为之的设置：

| 设置                         | 值 / 原因                                                             |
| ---------------------------- | --------------------------------------------------------------------- |
| `build.frontendDist`         | `../../web/dist` —— 复用网页版产物，桌面端没有自己的界面代码          |
| `build.beforeDevCommand/BuildCommand` | `pnpm --filter @invoice-tool/web dev/build`（前端先构建，Rust 才编译） |
| `app.windows[0].dragDropEnabled` | `false` —— 否则 Tauri 会接管拖放，网页版那套 DOM 拖放 + `<input type=file>` 就废了 |
| `app.security.csp`           | 生产 CSP：限制 `self` / wasm / worker / blob，网页版构建时由 Vite 注入同一份 meta |
| `capabilities/default.json`  | 只要 `core:default` —— 应用自己的命令不走 ACL，对话框是 Rust 侧发起的 |
| `bundle.icon`                | 5 个文件，由 `scripts/make-icon.mjs` 生成                              |

**图标不用 `npx tauri icon`**：`scripts/make-icon.mjs` 手写 PNG 编码器 + ICO 容器，
`.icns` 交给 macOS 的 `iconutil`。好处是不依赖 Tauri CLI 的版本与在线资源，
图标改一个颜色重跑一次就行。

⚠️ **`tauri::generate_context!` 在编译期就要把前端产物嵌进去**，
所以 Rust 侧编译之前必须先有 `apps/web/dist` —— CI 里那一步 `pnpm build` 不是可选项。

## 8. 验证状态（诚实账）

本机是 8 GB 的 MacBook Air。早先这里写着「桌面端在这台机器上**一次都没跑起来过**」——
**2026-10-18 这条被推翻了**：`-j 1` + 起飞前自检 + 看门狗之下，本机跑通了 debug 构建、
release 打包，并真的把打包出来的 app 启动了。已知与未知分开记：

**已经验证**：

- **本机真的构建、也真的启动了**（2026-10-18，全部 `CARGO_BUILD_JOBS=1`，看门狗在旁边）：
  - `cargo build -j 1`（debug，~120 crate + 链接）：1 m 11 s，进程树峰值 **744 MB**，
    产出 `target/debug/invoice-tool-desktop`（30.4 MB）。
  - `pnpm desktop:build`（= `tauri build`，release 全树冷编 + 链接 + 打包）：
    4 m 07 s，进程树峰值 **1178 MB**，产出 `发票工具.app`（31 MiB）与
    `发票工具_0.1.0_aarch64.dmg`（26.3 MB）。
  - **两种模式的界面来源不同，且都验过**：debug 二进制走 `devUrl`
    （必须有 Vite 在 5180，否则白屏）；release 包**内嵌** `web/dist`
    （二进制里有 asset 名册，实测运行时**一条 TCP 连接都没有**、也没连 5180）。
    release 那次前端 JS 确实跑过：数据目录 `logs/app.log` 里留下了前端经 `store`
    落盘的那一行（`intake ok: 4 张`）。
- 本机 `cargo check -j 2` 与 `cargo check --all-targets -j 2` **通过**
  （含 `tauri::generate_context!` 的前端产物嵌入、`build.rs` 生成能力 schema、
  以及 `#[cfg(test)]` 里的测试代码）—— 只产 metadata，没有链接，符合编译纪律。
  峰值内存 105–342 MB（看门狗实测），离 2500 MB 的上限很远。
- 看门狗的两条路都试过：正常跑打印峰值并退 0；`RUST_MAX_MEMORY_MB=1 pnpm desktop:check`
  在第一次采样就 `⛔ 已中止` + 退 1，事后 `ps` 里没有残留的 cargo/rustc。
- 起飞前自检的路也试过：门槛内打印一行 ✓ 并放行；`RUST_MIN_FREE_MB=99999` 时拒绝
  （退出码 1，**cargo 一次都没被起起来**），报告里挑出来的应用、给的 `osascript` 命令、
  以及「本会话，别动」的标记都对；`RUST_SKIP_PREFLIGHT=1` 能跳过。
- CI（`.github/workflows/ci.yml` 的 `desktop` job）：`cargo check` + `cargo test`
  （百分比解码、文件名清洗、打印机名解析、数据目录名字白名单）。

**只有单测验证、没在真机上跑过**：

- 12 个命令里除「数据目录写盘」之外的那些（对话框、交给系统打印、在访达里显示……）
- 单实例「第二次启动叫回已有窗口」
- 数据目录备份 / 恢复的端到端链路（序列化与恢复语义有单测）

> 真机上**唯一留下痕迹**的是 `store` 写盘：release 版启动后 `logs/app.log` 里出现了
> 前端经 IPC 写下的那一行，说明「前端 → 命令 → 数据目录」这条链是通的。
> 其余命令的行为仍然只有单测覆盖。

**还没做的**：

- CSP（现在是 `null`）
- macOS 公证 / 签名（`bundle.macOS.minimumSystemVersion: 10.15`，其余走 Tauri 默认）
- Windows 上 `-Verb Print` 的真实表现（依赖系统给 PDF 注册了「打印」动作）

> 本机验证到哪一步就够了：`cargo check --all-targets` 能挡住「写错了、类型不对、
> 缺 trait 实现」这类问题（`store_read` 曾经写成 `Option<Response>`，
> 而 `IpcResponse` 根本没为 `Option<Response>` 实现 —— 就是这一步挡下来的）。
> 它**挡不住**的是运行期行为：对话框弹不弹、打印机名解析对不对、路径写没写对。
> 那些只能等真机或 CI 的 `cargo test`。

**本机「到底能不能出二进制」，现在有实测答案：能。** 2026-10-18 冷编整套依赖树（release）
+ 链接 + 打包 = 4 m 07 s、峰值 1178 MB。先前根据磁盘残留（`target/debug` 里 170 个 `.rlib`
但没有最终二进制）推测「卡在链接那一步」—— 现在看更像是**当时被人为中止**，
而不是链接本身跑不动。`cargo check` 只产 `.rmeta`，所以那 170 个 `.rlib` 确实来自一次真 codegen。
顺带澄清一条旧笔记：`JetsamEvent-2026-10-16-091429.ips` 那次内存事件与 cargo 无关
（进程全是系统服务，且发生在开机两分钟后；`shutdown_stall` 是更早的另一份）—— 见 `AGENTS.md` §1。

## 9. 编译纪律（再说一遍）

- ✅ `cargo check -j 2`（只产 metadata）；本机的入口是 `pnpm desktop:check`
- ❌ 默认禁止 `cargo build` / `cargo test` / `cargo run` / `tauri build` / `tauri dev`
  —— 2026-10-18 实测它们在本机**跑得动**（见 §8），但默认仍然是禁止：
  一次几分钟、峰值 0.7–1.2 GB，而且突发可能出现在你走开之后。
  要走就明示放行：`ALLOW_RUST_BUILD=1 CARGO_BUILD_JOBS=1 …`
- ⛔ 同一时间只允许一个 cargo 进程
- 发布包**默认**在 `release.yml` 里构建（三平台矩阵）；本机出包是例外，不是常规路径

`apps/desktop/scripts/rust.mjs` 就是这条纪律的**执行者**：
本机跑 `pnpm desktop:dev` / `desktop:build` / `desktop:test:rust` 会被拒绝并告诉你为什么，
CI（`CI=true`）与明确设了 `ALLOW_RUST_BUILD=1` 的情况才放行。
它还是两道**内存闸**：链接类命令在启动之前先**自检**（可用内存不到 `RUST_MIN_FREE_MB`，
默认 3000 MB，就拒绝并列出该退哪个应用、怎么退），跑起来之后**看门狗**盯着
（进程树 RSS > `RUST_MAX_MEMORY_MB` 或系统可用内存 < `RUST_MIN_FREE_RATIO` 就 SIGKILL 整棵树）——
宁可这次检查失败，也不让机器重启。跳过硬跑：`RUST_SKIP_PREFLIGHT=1`。

**改前端不需要碰 Rust**：`pnpm dev` 就够了。只有改 `apps/desktop/src-tauri` 才碰 cargo。

## 10. 换壳评估：MyGo（2026-10-19，结论：不换）

问题：Rust 打包的痛，是不是换个壳就没了？

做法：把**真实的** `apps/web/dist` 装进 MyGo v0.5.5（Go + 系统 WebView），
