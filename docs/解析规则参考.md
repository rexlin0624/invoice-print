> 这份文档回答两个问题：**「票面长什么样」** 和 **「遇到一条文字该判成什么」**。
> 规则来自三处：① 真实数电票的实测坐标；② 参考实现 `fapiao-print`（`erma0/fapiao-print`
> 及其 AGENTS.md 里被踩出来的领域口径）；③ 本仓库 `packages/core` 的实现与测试。
>
> 凡是「还没做」的规则，都明确标了 `[M2]` / `[M3]` / `[M3+]`，不要当成已实现。
> 已完成的清单见 §8 的反面 —— 那一节只列**还没做**的。

## 1. 取数阶梯

```
XML 数电票 / OFD 内嵌 XML  >  二维码  >  PDF 文字层  >  OCR
      （结构化）              （结构化）    （版式推断）   （图像识别）
```

四层都已经实现（二维码见 §1.1，OCR 见 §7.6）。

**阶梯语义**：高可信度来源先落，低可信度**只补空缺，绝不覆盖**已确认的值。
每个字段带 `provenance = { source, confidence }`，UI 的 ⓘ 面板直接把来源显示出来。

| 来源 | 置信度 | 说明 |
| --- | --- | --- |
| `xml` | 0.99 | 数电票 XML，字段带标签 |
| `ofd` | 0.97 | OFD 内嵌 XML |
| `qr` | 0.95 | 票面二维码 |
| `pdf-text` | 0.85 | PDF 文字层 + 锚点定位 |
| `ocr` | 0.6 | 图像识别 |
| `derived` | 0.9 | 由其他字段推算（如 价税合计 = 不含税 + 税额） |
| `manual` | 1 | 用户手改 |

**字段置信度被来源封顶**：`mergeExtraction()` 写入时取
`confidence = Math.min(字段自身的置信度, SOURCE_CONFIDENCE[来源])`。
理由：OCR 认出来的「发票号码」哪怕格式完美，也不该比二维码更可信；
`extractInvoiceFields()` 内部用的是同一套规则、同一套 `CONF.strong/medium/weak`
（0.9 / 0.75 / 0.55），**不按来源分叉** —— 封顶这件事只在合并这一层做一次。
所以 `pdf-text` 的强字段是 `min(0.9, 0.85) = 0.85`，`ocr` 的强字段是 `min(0.9, 0.6) = 0.6`
（实测：扫描件解析出销售方名称，`provenance = {source:'ocr', confidence:0.6}`）。

⚠️ **执行顺序 ≠ 优先级顺序。** 二维码要先栅格化才能读，所以实际是
「文字层先跑、二维码后跑」，但合并时按置信度取胜，二维码（0.95）会盖掉文字层（0.85）。
`mergeExtraction()` 里**必须**先比置信度再决定跳不跳 ——
历史上写错过一次（「已有值就 continue」），结果是阶梯变成死代码，
二维码永远盖不过先跑的 PDF 文字层。回归见 `samples.test.ts` 的
「二维码与文字层一致，且按阶梯取自二维码」。

**与参考实现的差异（有意为之）**：参考实现的优先级是 `PDF 文字层 > OFD XML > XML 数电票 > OCR`，
它把 PDF 文字层放最前，因为它的 XML 路径当时只能做列表展示、不进排版。
本仓库把结构化数据放最前，理由：**XML/OFD/二维码里字段是无歧义的，不存在「猜哪一列是销售方」的问题**；
PDF 文字层是版式推断，永远有猜错的概率。顺序改了，风险方向就对了。

### 1.1 二维码（实测格式）

数电票的二维码固定在**票面左上角**。两张真票实解出来：

```
01,32,,12345678901234567890,55.58,20260619,,300A        ← 合成样本A
01,32,,10987654321098765432,19.87,20260622,,6283          ← 合成样本B

01,32,,12345678901234567890,55.58,20260619,,300A
│  │  │  │                    │       │        │ └ 4 位尾码（用途未公开，只做诊断）
│  │  │  │                    │       │        └─── 校验码（数电票为空；老税控票 20 位）
│  │  │  │                    │       └──────────── 开票日期 YYYYMMDD
│  │  │  │                    └──────────────────── 价税合计（元）
│  │  │  └───────────────────────────────────────── 发票号码
│  │  └──────────────────────────────────────────── 发票代码（数电票为空）
│  └─────────────────────────────────────────────── 票种代码（32 = 电子发票（普通发票））
└───────────────────────────────────────────────── 固定头 01
```

**为什么值得解**：它由税务系统按同一份数据生成，**号码 / 价税合计 / 开票日期**
三个最要紧的字段与票面绑定得没有歧义，正好在文字层「取错 token」时兜底，
也能反过来给文字层挑错。销售方名称、不含税金额、税额**都不在二维码里**，不要凭空造。

**职责边界**：内核只认二维码里的**字符串**（`parse/qr.ts`）；
图像 → 字符串要栅格化 + WASM，属外壳能力（`apps/web/src/lib/qr.ts`），
解出来的原文经 `ParseInput.qrPayload` 注入。

**认不出来就整条丢弃**：票面可能还印着官网/小程序/验真链接的二维码。
判据是「头必须是 `01`」+「号码必须是 8 位或 20 位纯数字」+「日期必须合法」，
三者任一不满足就 `undefined`，绝不拿它当真票数据。

**冲突怎么办：报，而不是偷偷改。** 二维码与文字层在
号码/金额/日期任一上不一致，就发一条 `qr-mismatch` 警告并列出两个值，
让人工核对。合并仍按阶梯走（二维码胜出），但用户**看得见**发生过不一致 ——
静默改掉一个用户已经在预览里看过、且肉眼可核对的数字，比报警更糟。

**票种代码只用来「补空缺」和「同族校验」**：
文字层没判出票种时，用代码补一个粗分类；只有增值税家族（31/32）才做
「专票 / 普票」交叉校验 —— 否则「通行费票（toll）+ 代码 32（普票）」会天天误报，
因为通行费本身就是普票的一种，只是业务上更具体。代码 51/52/61 的映射
来自票种代码表但**没有真样本验证过**，所以不参与校验。

**本地优先**：zxing 默认从 jsDelivr CDN 拉 `.wasm`。本仓库把 wasm 打进产物，
并**自己取回来以 `wasmBinary` 交给 Emscripten**，让胶水代码根本不会去解析路径 ——
「不可能走 CDN」从机制上保证，而不是靠一条升级后可能失效的覆盖。
（实测：导入发票全程零外部请求。）
解码器走动态 `import()`，首屏不为这 1 MB 买单。

**置信度档位**（`parse/fields.ts` 的 `CONF`）：

| 档位 | 值 | 含义 | 例子 |
| --- | --- | --- | --- |
| `strong` | 0.9 | 锚点明确命中 | 「价税合计…（小写）¥55.58」 |
| `medium` | 0.75 | 正则全文匹配 | 全文里的 `2026年06月19日` |
| `weak` | 0.55 | 兜底推断 | 全文第一个 20 位数字当发票号码 |

## 2. 票种判定

顺序即优先级，**先窄后宽**（`KIND_RULES`）。窄的、有强标记的排前面，
否则会被宽的规则抢走。

```
铁路电子客票 / 中国铁路       → train
航空运输电子客票行程单        → air
非税收入 / 财政票据           → nontax
医疗收费 / 门诊 / 住院        → medical
车船税                        → vehicle-tax
出租车 / 出租汽车             → taxi
网约车 / 滴滴                 → ride
通行费                        → toll
增值税专用发票 / 专用发票     → vat-special
电子发票（普通发票）/ 普通发票 → vat-general
以上都不中                    → unknown
```

### 2.1 两条必须记住的顺序陷阱

**① `medical` 必须早于 `nontax`。**
医疗收费票据上同时有「票据代码 / 票据号码 / 交款人」，这三个词是 `nontax` 的判据。
把 `nontax` 放前面，医疗票会被判成非税票。

**② `vat-general`（普票）要早于 / 优先于 `vat-special`（专票）。**
票面别处可能出现「专用」字样（如「成品油专用」业务标签），
若先匹配「专用发票」会把普票误判成专票。参考实现的做法：只在 VAT 分支里判子类型，
且**票头标题区（`ny < 0.18`，即页面上方 18%）优先**，全文兜底。

### 2.2 弱信号需要「≥2 组」才认

火车票的弱信号有 13 组：`车次 / 票价 / 座位 / 席别 / 检票 / 进站 / 出站 / 铁路 / 乘车 / 二等 / 一等 / 动车 / 高铁`。
命中 **≥2 组**才判为车票 —— 单组命中不足以判，否则一张写着「票价」的增值税票会被误判成车票。

通行费同理：`通行费` 是强标记直接判；否则需要「车牌号 / 车牌颜色」+「通行日期」**双组**。

### 2.3 业务标签与票种是两件事

「成品油」「通行费」「旅客运输服务」「货物运输服务」「建筑服务」「不动产经营租赁」
「医疗服务」「旅游服务」「不动产销售」是**特定业务标签**（数电票左上角那个小字），
它不改变票种。一张「成品油」的票仍然是普票。
所以模型里 `kind` 和 `businessTag` 是两个字段，UI 上也是两个 chip。

## 3. 真票实测版式（数电票横版）

实测尺寸 **595.28 × 396.85 pt**（≈ A4 横版的 2/3 高），两张真票一致。

```
y≈39   [QR 码]                        电子发票（普通发票）
y≈39                                  发票号码：12345678901234567890
y≈57                                  开票日期：2026年06月19日
y≈103  名称：<购买方>                        名称：<销售方>
y≈133  统一社会信用代码/纳税人识别号：<...>      统一社会信用代码/纳税人识别号：<...>
y≈268  合计  ¥52.58  ¥3.00
y≈286  价税合计（大写）伍拾伍圆伍角捌分（小写）¥55.58
```

**关键：购销方是左右分栏，两栏的「名称：」在同一个视觉行上。**
国家票面标准是购买方在左/上、销售方在右/下，所以按阅读顺序（先 y 后 x）拼出来的
第 1 个「名称：」是**购买方**，第 2 个是**销售方**。

这直接决定了核心的排版坐标系选择（见 §5）。

## 4. 字段抽取规则

全部走 **锚点文字 + 相对位置**，不使用任何绝对坐标。

### 4.1 发票号码

1. 锚点 `发票号码：` → 同一 token 里的行内值 → 否则读右侧 token（最多 6 个，遇下一栏标签就停）
2. 从候选里取 `\d{20}`（数电票），否则 `\b\d{8}\b`（老票），否则 `\d{8,25}`
3. 兜底：全文 `\d{20}`，置信度 `weak`

### 4.2 开票日期

归一化支持 `2026年06月19日` / `2026-06-19` / `2026/06/19` / `2026.06.19` / `20260619`，
输出统一 `YYYY-MM-DD`。合法性闸门：年 1990–2100、月 1–12、日 1–31。
**不做时钟推断**：`normalizeDate` 不补月补日，拿不到完整日期就返回 `undefined`。

### 4.3 购销方名称 / 税号

- 名称锚点：`名称：` / `名称:` / `名 称：`（CJK 拆字：PDF 文字层会把「名称：」拆成单字 token，见 §4.7）
- 税号锚点：`统一社会信用代码/纳税人识别号：` / `纳税人识别号：` / `统一社会信用代码：`
- 取值：锚点右侧 token 拼接到「下一栏标签」之前（见下面两条边界规则）
- 停止标签集合 `COLUMN_STOP` = 名称锚点 ∪ 税号锚点 —— 这是「读右不过界」的关键，
  否则左边的购买方会把右边的销售方一起吞进去

两条边界规则（都是实测踩出来的）：

1. **大空档就停**：已经取到至少一个 token 后，若下一个 token 与当前的右边界相距超过
   `max(6, 1.5 × 行内中位字高)`，视为换栏，停止。
   实测：购买方名字后面跟着右栏表头的「销」，不设这条就会拼成
   「某某测试甲有限公司**销**」。
2. **按字符数封顶**（48 字 / 24 个 token），**不按 token 数**封顶。
   文字层里「某某测试销售…」通常是一个 token，而 OCR 会把它切成一个个单字 ——
   早先写死「最多 6 个 token」，在 OCR 上会把公司名截成 6 个字。

**只有一个「名称：」锚点**（竖版票 / 单栏票，OCR 认丢第一栏也走这里）时，归属按两条依据推断：

1. 全文前 400 字里有没有「销售方」字样；
2. **位置**：国家票面标准是购销方左右分栏、**购买方在左、销售方在右**，
   所以锚点在页宽右半 → 判给 `sellerName`。

无论哪一条成立，都**必须发一条 `low-confidence` 提示**让人工确认。
`anchors.sellerName` 会写明是靠「销售方」还是靠「右半栏位置」判的。

⚠️ 这一段的分支必须是 **if / else-if 互斥**：历史上写成 `if (命中数 >= 1)` 后面再
`if (>= 2) … else if (=== 1)`，只有一个「名称：」时两个分支都会跑，
结果**购买方和销售方被塞成同一个名字**。回归见 `fields.test.ts` 的
「只剩一个「名称：」时的归属推断」。

`[M2]` 更完整的购销方判定（参考实现有，本仓库只做了其中一部分）：

- 表头 x 坐标区域锚点（`_determineLabelSide()` + `_getSideBoundary()`）—— **未做**，
  只做了上面那条「锚点在右半页 → 销售方」的简化版；
- 四条交叉校验（同名清空、位置反了交换、信用代码位置交换、同侧迁移）—— 只做了两条
  （见 §2 的 `validate.crossCheckParties`）：`sellerName === buyerName` 或
  `sellerTaxId === buyerTaxId` → 发 `party-suspect` 警告，**只报不改**。
  需要坐标的那两条**没有做**。

### 4.4 金额三件套

| 字段 | 主路径 | 兜底 |
| --- | --- | --- |
| `amount` 不含税 | 「合计」行（**排除**「价税合计」行）的第 1 个金额 | — |
| `tax` 税额 | 「合计」行的第 2 个金额 | — |
| `total` 价税合计 | 「价税合计」行的**中文大写** → `capitalToCents()` | ①行内「（小写）¥nnn.nn」②`amount + tax` 推算（`medium`） |

- 金额一律 **整数「分」**（`number`），禁止浮点存元。
- `findAmounts()` 只认带小数点的数（发票金额必带两位小数），
  整数金额**必须带货币符号**才认 —— 否则会把「2026」当金额。
- 中文大写解析 `capitalToCents()` 覆盖 `零壹贰叁肆伍陆柒捌玖拾佰仟万亿圆元角分整正〇`。
- `[M2]` 数学验证配对 + 区域解析三阶段；校验失败时列表卡片打 ⚠ 徽章并进汇总计数。

### 4.5 校验码 / 发票代码

- 校验码：锚点 `校验码：`，取 `\d[\d\s]{15,30}`，**去掉所有空白**（票面按 4 段分组印刷）
- 发票代码：锚点 `发票代码：`，取 `\d{10,12}`（老票才有）

### 4.6 票面「开票人」

开票人**不是发票要素**，不进 `Invoice` 模型。但保留 `anchors.drawer`
（`Extraction.anchors` 里唯一一个非模型键），用于 UI 展示和排查问题。

### 4.7 CJK 拆字（必须在所有匹配之前做）

某些 OFD / PDF 生成器会把一个词拆成**每字一个 token**（如「名」「称」「：」），
甚至插入空格。所以**所有文本匹配前先 `squash()`**（去空白 + 全角转半角），
再做包含判断；需要定位 token 时用「逐字成词」的锚点扫描（`findLabelTokens`）。

- 名称括号保留原文（`（广州）` 不能变成 `(广州)` —— 财务对抬头是全字符比对的）
- 「年/MM/月/DD/日」这种被拆散的日期序列要能合并后再归一化

## 5. 坐标与排版语义（全链路约定）

### 5.1 旋转

**正值 = 顺时针**（与 CSS `rotate(N deg)` 一致）。

- **内核**只输出 `rotation: 0 | 90`（`fit()` 比较「不旋转」与「转 90°」哪个缩放大，取大的）。
- **预览**（CSS）：直接 `rotate(90deg)`。
- **PDF**（pdf-lib）：`drawImage/drawPage` 的 `rotate` **绕 (x, y) 锚点、正角度为逆时针**，
  所以必须传 `degrees(-rot)`，并把锚点从内容盒左下角换算成**旋转后包围盒**的左下角。
  本仓库 `print.ts` 的 `drawEmbedded()` 推导：内容本地占 `(w,h)`，顺时针转 90° 后包围盒为
  `x∈[-h,0]、y∈[0,w]`；要落到 `x∈[L,L+h]、y∈[B,B+w]`，原点放 `(L+h, B)`，并传**未旋转**的 `(w,h)`。
- 验证方法：红色象限测试源 + 渲染输出找红色质心，断言落点象限。本仓库已用 qlmanage 渲染实测通过
  （`allowRotation: true` + 竖向 + 每页 4 张 → 两张横版票各转 90°，无偏移、无裁切）。

### 5.2 y 轴方向

**内核只输出一次几何**（单位 pt，**y 轴向下**，原点左上）。两端各写一个**极薄适配器**：

- CSS：`top = y * zoom`，直接用，不换算。
- PDF：`flipY(pageHeight, y, h) = pageHeight - (y + h)`，**全流程只翻这一次**。

⚠️ **参考项目在这里踩过坑**：预览与打印各算一套几何，导致五处需要同步
（`renderPage` / 拖拽偏移约束 / `setSlotAlignment` / Rust lopdf / Rust printpdf）。
本仓库的原则是「几何只算一次」，适配器里**不允许**出现 `if (旋转) 重新算宽高` 这种逻辑。

### 5.3 裁切线

`LayoutSpec` **不携带** `cutLines`（它是「画不画」的显示开关，不是几何）。
`cutLines` 由外壳作为独立参数传给预览与 `composePrintPdf`，
两者都基于 **slot 的实际边界**（`slot.x/y/w/h`，含内边距）画虚线，
预览与 PDF 才对得上。

## 6. 查重（三层，安全边界是重点）

| 层 | key | 判定 | 动作 |
| --- | --- | --- | --- |
| 文件级 | `sha256(字节)` | 内容完全相同 | **自动跳过** |
| 业务级 | `发票号码` | 同一张票（PDF 与 OFD 各一份也会命中） | **自动跳过**，保留 `completeness()` 最高的那张（xml/ofd 来源 +2 分） |
| 疑似级 | `销售方 + 价税合计 + 开票日期` | 号码不同但三要素相同 | **只标记，绝不自动跳过** |

**安全边界**：自动跳过只信任「文件相同」和「发票号码相同」。
「销售方 + 金额 + 日期」看似很准，但**同一天在同一家店买两次同价的东西是真的会发生**，
所以它只能标记、交人工核对。

`[M2]` 多页发票的「逻辑票」聚合：同一个 PDF 的续页不能被当成重复删掉（否则打印缺页）。
参考实现按 `_invoiceGroupId` **整组计数、整组删除**。

## 7. 已知坑（都是血换来的）

### 7.1 pdfjs 会转移（transfer）你传给它的字节

```
Cannot perform Construct on a detached ArrayBuffer
```

pdfjs 把 `data` 的 `ArrayBuffer` **转移**给它的 worker。转移之后调用方手里的
`Uint8Array` 就变成 detached：`byteLength` 静默变 **0**（不抛错！），再 `slice()/subarray()` 才抛。

**这个 bug 只在浏览器里出现**（Node 无 worker，不转移），所以典型症状是
**「单元测试全绿、网页里全空」**。

- 内核侧：`parse/pdfText.ts` 交出去之前 `data.slice()` 拷一份。
- 外壳侧：统一走 `apps/web/src/lib/pdfjsSafe.ts` 的 `safeBytes()`。
- 实测踩到的具体形态：预览缩略图先渲染（那次调用把字节弄坏了），
  等用户点「下载 PDF」时 `item.data.byteLength` 已是 0 → 静默退化成「信息卡」而不是嵌原票面。

### 7.2 内容流顺序 ≠ 视觉顺序

PDF 文字层的 token 顺序是**内容流顺序**，不是阅读顺序。
`text/lines.ts` 的做法：先按 y 分 band，**band 内严格按 x 排序**。
得到的 `text` 才是人眼看到的顺序。

容差**不能写死 2pt**：文字层同一行的基线几乎一致，2pt 够用；但 OCR 给的是每个词的紧贴框，
同一行的 y 会差几个像素（见 §7.7）。现在的规则是
`容差 = max(2pt, 页内中位字高 × 0.25)` —— 字号大，同一行的抖动绝对值也大。
另外要保证「表头行」和「名称行」不被合并：实测「购买方/销售方」表头基线只比名称行高 **2.8pt**，
而字高 9pt（容差 2.25pt），刚好分得开 —— 这两行的间距就是当初把容差从 2pt 抬到自适应时的边界案例。

### 7.3 长数字导出必须强制文本

≥15 位纯数字（20 位发票号、18 位税号）如果按数字写进 CSV/Excel，
会被转成科学计数法**并丢精度**（`12345678901234567890` → `1.2346E+19`，末几位变 0），
报销时对不上账。

**CSV 里加引号不管用** —— Excel 会脱掉引号再当数字解析。
唯一可靠的做法是写成公式：`="12345678901234567890"`。
`invoicesToCsv()` 已实现（`/^\d{15,}$/` → 包裹）。`[M2]` 换成真 `.xlsx` 后由单元格格式接管。

### 7.4 合计行与价税合计行必须分开找

「合计」是 `includes('合计')`，「价税合计」里也含「合计」。
只写 `includes('合计')` 会把价税合计行当合计行，于是 `amount` 取到税额、`tax` 取到价税合计。
必须 `includes('合计') && !includes('价税合计')`。

### 7.5 解析器不抛异常

所有解析函数返回 `{ 结果, issues[] }`，绝不 `throw`。
`issues` 里每一条都带 `field`，UI 能直接定位到那一格让用户改。
字段拿不到就是 `undefined`，**不要用空串或 0 冒充**。

### 7.6 OCR 的分工：外壳出「词表」，内核照旧抽字段

OCR 不另开一条取数路径，而是**伪造一份和文字层结构完全相同的输入**：

```
图片/扫描页 ──(外壳 tesseract.js)──> OcrPageInput { width, height, tokens: TextToken[] }
                                              │
                                              ▼
                      buildPageText → buildDocumentText → extractInvoiceFields
                                            （与 pdf-text 同一套代码，来源标 'ocr'）
```

- 外壳只做「像素 → 词 + 框」，**不认任何发票字段**；
- 内核拿到的就是 `TextToken[]`，普通得和 pdfjs 给的一模一样；
- 词框坐标要**除以渲染缩放比**回到原图坐标系（识别画布宽度封顶 1600px，避免 8GB 机器上翻车）；
- 置信度 < 10 的词丢掉：中文单字在 tesseract 里置信度波动极大（实测同一行里有 89 也有 4），
  阈值设 20 会把「体」「州」「公」这类**正确但低分**的字丢掉，公司名就残了；
  而表格边框、印章这类噪声的置信度反而常常很高，所以这个阈值只用来挡明显乱码。
- OCR 一定发 `ocr-used` 提示；模型文件缺失发 `ocr-unavailable`，超时发 `ocr-timeout`。

实测（`qlmanage` 生成的 1800×1199 扫描件，含二维码）：
`发票号码 / 价税合计 / 开票日期` 来自二维码（0.95），
`销售方名称` 来自 OCR（0.6，缺字：`广东广州石油分司`），购买方未取到（第一栏标签被认丢）。

### 7.7 OCR 的词框让「按 y 分行」失效

tesseract 给的是每个词的**紧贴框**，同一视觉行里各字的 y 会差几个像素；
而固定 2pt 容差是给文字层（基线几乎完全相同）设计的。后果非常隐蔽：

```
一张扫描件被拼成 48 行、每行一两个字
→ 「名称：」永远不在同一行里 → 锚点全部失配 → 字段全空
```

修法见 §7.2：容差随字号走。另外 `TextToken.y` 对文字层是**基线**、对 OCR 是**框顶** ——
分行只比较相对顺序，所以可以共用一套，但**不要**把 `y` 当精确的框顶去算几何。

### 7.8 tesseract.js 的返回结构：`blocks` 默认关，词在嵌套里

两个坑叠在一起，后果是「OCR 明明跑成功了，但一个字都没进内核」：

```js
const r = await worker.recognize(canvas);        // ❌ v6/v7 里 data.words 不存在
r.data.words                                     // undefined → 空数组 → 字段全空
await worker.recognize(canvas, {}, { blocks: true });  // ✅ 必须显式要
r.data.blocks[].paragraphs[].lines[].words[]     // 词在这里
```

- v4 顶层有 `data.words`，v6/v7 只有嵌套的 `blocks[].paragraphs[].lines[].words[]`；
- 而且 `blocks` **默认不生成**（见包内 `worker-script/constants/defaultOutput.js`，默认只有 `text: true`）；
- 所以 `apps/web/src/lib/ocr.ts` 里走了三条路：v7 的 blocks → v4 的 words → TSV 解析兜底，
  换版本时不会静默退化成「识别成功但零字段」。

### 7.9 标签会被切碎：锚点要在**行文本**上匹配

OCR 把「名称：」切成「名」「称」「:」三个 token，前面还可能粘着边框噪声变成「|名」。
`findLabelTokens()` 原来要求「**单个 token** 以标签开头」，于是永远匹配不上。

现在两条路径：

1. 单 token 就带标签（文字层常态）→ 直接用原 token，`inlineValue()` 继续可用；
2. 否则在**整行归一化文本**里找标签，把命中的字符区间映射回 token：
   - 跨 token → 合成一个区间 token（text 从标签首字开始），`index` 指向标签**结束**的 token；
   - 落在同一个 token 内但不在开头（噪声前缀）→ 从标签首字切一段当 token。

另外，购销方取值必须把 `inlineValue(hit)` 也算上 —— 早先只读锚点**右侧**的 token，
遇到「名称：某某测试甲有限公司」这种内联写法就会漏。

### 7.10 后台标签页里 canvas 渲染会被暂停 → **已搬进 Worker**

pdfjs 的 `page.render()` 在主线程上依赖 `requestAnimationFrame` 分片推进。
标签页不可见（或窗口被完全遮挡）时 Chrome 会**暂停 rAF**，于是 render 永远不 resolve，
整个导入流程卡死 —— 而这几个用途（二维码、裁白边、黑白/栅格化、OCR 前的栅格化）
**全都是可选增强**，绝不能拖死主流程。

**2026-10 的修法是釜底抽薪**：把画布渲染整体搬进 Worker
（`apps/web/src/lib/render.worker.ts` + `render/engine.ts`，客户端 `render/client.ts`）。
pdfjs 源码里那行是
`_useRequestAnimationFrame = useRequestAnimationFrame === true && typeof window !== "undefined"`，
Worker 里没有 `window`，于是渲染推进改用**微任务**（`Promise.resolve().then`）——
微任务既不受 rAF 暂停影响，也不受后台标签页的定时器节流影响。
换句话说：这条路径现在与标签页可见性**彻底无关**了。

`apps/web/src/lib/timeout.ts` 的 `withTimeout(work, ms, label)` 仍然保留（超时返回 `undefined` 并 `console.warn`），
因为「坏文件 / 超大页 / 老浏览器退回主线程」这些情况依然存在：
二维码 15s、OCR 120s、裁白边 15s。
当年的实测证据：`getOperatorList()` 37ms 正常、`render()` 无限等待，
而 `setTimeout`/微任务/MessageChannel 都**不受影响** —— 所以那是 rAF 暂停，不是定时器节流。

## 9. 改动本文件的前提

改解析规则必须同时改三处，否则不算改完：

1. `packages/core/src/parse/*`（实现）
2. `packages/core/test/*`（回归；`test/samples.test.ts` 会拿 `samples/` 里的真票全字段比对）
3. 本文件（口径）

字段准确率低于基线**不允许合并**。

改**外壳渲染**（`apps/web/src/lib/render/**`、`raster.ts`、`thumb.ts`、`qr.ts`、`ocr.ts`
里画图那一段）也有对应的门槛，因为内核单测碰不到 canvas：

```bash
pnpm typecheck && pnpm test && pnpm e2e   # e2e = 无头 Chrome 里的 12 项渲染回归
```

渲染回归的夹具是 pdf-lib 现场生成的（黑块画在已知位置），所以能断言**像素级**结论，
不依赖 `samples/private/` 里那些真实发票（那是个人数据，不该成为测试前提）。
